# 멀티에이전트 파이프라인 전략·로드맵

> 지속 관리 영역(area). Claude(구현)↔Codex(검수) 파이프라인을 언제·어떻게 쓰고 어디로 발전시킬지 기록.

## 현재 구조 (2026-05-26)
- **Generator–Critic 패턴**: Claude=생성(계획·구현·수정), Codex=검수.
- **교차 모델**: 서로 다른 모델(Claude/Codex)이라 사각지대가 달라 자기검토보다 많이 잡는다.
- **결정론적 오케스트레이터**: `.local/review-pipeline/review_loop.sh`가 루프 소유, 에이전트 직접 호출 금지.
- **무한루프 5겹**: ①하드캡 ②BLOCKER 게이팅 ③정체 감지 ④VERDICT 토큰 ⑤이견→사람.

## 왜 이 케이스에 값을 하나 (사용자 의도)
멀티에이전트가 값을 하는 조건과 본 프로젝트의 대응:
1. **교차검증 가치가 진짜 있을 때** ✅ — 작업이 "사용자 아이디어 → 코드 구현"이라, 비교·반복할수록 결과가 좋아진다. (핵심 동기.)
2. **역할 분업** ✅ — 생성과 검수를 다른 모델이 전담.
3. **장시간 무인 실행에 안전 리뷰어 필요** ✅ — 자동 분석·배치가 도는 동안 품질 게이트 역할.

→ 단일 에이전트로 충분한 단순 작업엔 과하지만, 위 3조건이 맞는 본 프로젝트엔 적합. **새 작업마다 "이 3조건에 해당하나?"를 먼저 판단**하고 멀티에이전트 적용 여부를 정한다.

## 로드맵
### 1. 하이브리드 — 싼 결정론적 검사를 루프 앞단에 (우선)
기계가 잡을 수 있는 건 기계로, Codex는 판단이 필요한 것만.
- `review_loop.sh` 앞에 **eslint(console.log·any 등), tsc(타입), 테스트(회귀)** 선검사 추가.
- 이게 BLOCKER면 Codex 호출 전에 Claude가 먼저 수정 → 토큰·시간 절약.
- Codex는 **설계·의도·로직 타당성** 등 기계가 못 보는 것에 집중.
- (오늘 `any`·`console.log`는 사실 eslint가 공짜로 잡을 수 있던 것 → 하이브리드의 필요성 입증.)

### 2. eslint 도입 (사용자 미경험 → 추후 학습+도입)
- 프로젝트에 eslint 설정이 약하거나 없음. flat config + @typescript-eslint로 `no-explicit-any`, `no-console` 등 규칙화.
- 도입하면 하이브리드 1번의 선검사 재료가 됨.

### 3. (선택) 프레임워크 검토
- 규모 커지면 LangGraph/CrewAI/AutoGen/Agents SDK 고려. 지금은 손수 만든 bash가 더 단순·투명·통제 가능하므로 유지.

## 트레이드오프 (잊지 말 것)
- 비용: 검수 1회 = Codex 풀 실행(토큰). 기계적 이슈엔 과함 → 하이브리드로 완화.
- 지연: 라운드당 수 분.
- 두 LLM이 동시에 확신하며 틀릴 수 있음 → "캡에서 사람 판정"이 안전장치.
