줌 자기장 로컬라이제이션 — 6개 방법 메뉴

Claude↔Codex 5라운드 토론 산출 · 2026-05-27 · 사용자가 직접 비교·판단하기 위한 보고서

읽는 법. 줌 화면에서 자기장(특히 다음 페이즈 원)의 절대좌표를 무마찰로 복원하는 6개 완결 파이프라인이다. 검증된 사실 위에서 비교한다 — 줌 지형 매칭(SIFT)은 라이브 실패 확정, 줌 흰 원 RANSAC 검출은 성공(inlier 25~39%). 최고 = 정확도 천장 최고(이상), 최선 = 첫 빌드 현실 추천.
핵심 정정 반영. 사용자: "플레이어가 가장자리를 보려고 줌하지 않는다." → 줌 프레임에 플레이어 아이콘이 들어있을 가능성이 높다. 이전 라운드에서 강등했던 플레이어 아이콘 앵커가 2·3페 주력으로 복귀했다.

phase 구간별 주력 (정정 반영)

Phase존 크기주력플레이어 아이콘
2·3페큼플레이어 앵커 + 줌레벨 scale + 원 ruler 교차검증주력
4페중간플레이어 앵커 + 원 ruler + 조건부 미니맵 F공동 주력
5·6페작음미니맵 경계기하 F + 플레이어 앵커 + multi-frame 합의공동 주력

방법 상세

최선

1플레이어 앵커 공지윈도우 lock

동작
  1. 공지 윈도우 N프레임 수집.
  2. 줌서 플레이어 아이콘 검출.
  3. 아는 P_world와 연결.
  4. 줌레벨 scale 후보화.
  5. 흰 원·parent containment gate.
  6. N-of-M 합의 transform만 commit.
정확도 천장: 높음. P_world 절대 anchor 잡히면 지형매칭 없이 viewport 확정.
실패모드: 아이콘 미검출·UI겹침·P_world drift·scale 오류.
미측정 가정: 윈도우서 아이콘이 충분히 자주 보임.

2원 ruler 재앵커

동작
  1. 전체맵서 기존 원(중심·반경) 저장.
  2. 줌서 흰 원 arc RANSAC.
  3. 반경비로 scale 후보.
  4. arc 중심 기준 translation 역산.
  5. parent·phase로 불가능 후보 제거.
  6. cluster 안정 시 commit.
정확도 천장: 중상. arc 길고 깨끗하면 강, 반경 단독 scale은 aliasing.
실패모드: 현재/다음 원 혼동·짧은 arc·흰 UI 노이즈.
강점: 필요 검출이 전부 이미 검증된 흰 원 RANSAC. P_world 불필요.

3미니맵 경계기하 F

동작
  1. 미니맵서 경계 arc 검출.
  2. 중심·회전·scale로 viewport 후보.
  3. 전체맵 원·phase로 후보 축소.
  4. 줌 arc/아이콘 gate.
  5. 후반 F 후보 commit.
정확도 천장: 중상. 후반 작은 원서 기하제약 강함. 줌 글랜스 불필요.
실패모드: 중반 큰 원 arc 평평·미니맵 회전 drift·UI 가림.
미측정 가정: 후반 경계 arc 가시·회전·중심 drift 제어 가능.

4결정론 지도앵커

동작
  1. 줌서 라벨·해안·도로·건물 윤곽 검출.
  2. 사전 anchor index 매칭.
  3. transform 후보 생성.
  4. 원 ruler·아이콘 gate.
  5. multi-frame 반복 시 commit.
정확도 천장: 높지만 첫 빌드 난이도도 높음.
실패모드: 테마변화·라벨가림·배율별 스타일·anchor 희소 구역.
미측정 가정: 렌더가 사전지도와 결정론적으로 일치.
최고

5factor graph 융합

동작
  1. 윈도우 동안 아이콘·원·F·scale·지도앵커 전부 관측.
  2. 각 관측을 factor화(신뢰도·오차모델).
  3. viewport·scale·translation·phase를 latent로.
  4. parent·phase hard constraint.
  5. N프레임 최적화, posterior 최협 commit.
  6. 낮으면 보류, 기존 원 유지.
정확도 천장: 6개 중 최고. 단일 검출 실패에 강함.
실패모드: 오차모델 틀리면 헛confidence·복잡도·디버깅 난이도.
미측정 가정: primitive false-positive 분포 추정할 데이터 축적.

6ML retrieval 줌 위치검색

동작
  1. 전체맵을 zoom·crop·style 합성 → retrieval index.
  2. 줌 crop embedding 변환.
  3. nearest crop 후보 검색.
  4. 원·아이콘·phase 재랭킹.
  5. multi-frame 수렴 시 commit.
정확도 천장: 높을 수 있으나 데이터·운영 난이도 큼.
실패모드: domain gap·맵업데이트·유사지형 반복·학습 편향.
미측정 가정: 합성-실제 시각차를 retrieval이 견딤.
Codex 추천 (최선). 첫 빌드는 방법 1(플레이어 앵커 윈도우 lock). 사용자 정정 후 플레이어 아이콘이 가장 값싼 절대 anchor로 복귀했고, 검증된 흰 원 RANSAC을 gate로 붙이면 단독 아이콘 검출 위험을 낮출 수 있다. factor graph(최고)는 최종형이지만 첫 빌드엔 미측정 primitive가 너무 많다.
Claude 이견. 첫 빌드 최선은 방법 2(원 ruler)가 더 안전하다. 방법 1은 미검증 검출(플레이어 아이콘)과 P_world 부트스트랩 의존을 새로 추가하지만, 방법 2는 필요한 검출이 전부 이미 라이브 검증된 흰 원 RANSAC뿐이고 이미 락된 현재 원이 그대로 절대 anchor+자(ruler)가 된다. 실용 절충: 방법 2를 코어로 먼저, 같은 commit/gate 프레임워크 위에 방법 1을 두 번째 anchor 소스로 추가(1+2 동시). 다음 원만 보일 때만 플레이어 앵커가 필요하므로 둘은 상보적이다.
빌드 전 측정 — 어느 방법이든 이게 먼저다 (녹화로 즉시).
  1. phase 2~6별, 공지 윈도우 줌 프레임 안 플레이어 아이콘 가시율·검출률. → 방법 1 가치 확정.
  2. 같은 윈도우 흰 원 arc 검출률 + 현재/다음 원 혼동률. → 방법 2 가치 확정.
