발견된 버그 3개

CRITICAL 버그 1 — 전체 화면 좌표를 맵 좌표로 착각

캡처된 이미지는 전체 게임 화면 (1920×1080)이지만,
PUBG 전체맵에서 실제 지도 영역은 화면 중앙에 약 1080×1080 크기의 정사각형으로만 표시됨.

circle.service.ts는 전체 화면 기준으로 정규화하지만,
CircleOverlay + Leaflet 맵 이미지는 지도 이미지 기준 [0,1]×[0,1]을 사용함.
→ 결과적으로 원의 위치가 가로 방향으로 압축되어 표시됨.
// 현재 코드 (circle.service.ts:47-51) return { x: circle.cx / width, // 1920 기준 → x=0.5가 화면 중앙 y: circle.cy / height, // 1080 기준 → y=0.5가 화면 중앙 r: circle.r / Math.min(width, height), // min=1080 기준 }; // 문제: // 실제 맵 영역이 x=[420, 1500] 범위라면 // 맵 중심 cx=960 → x = 960/1920 = 0.5 (우연히 맞음) // 하지만 맵 좌측 cx=450 → x = 450/1920 = 0.23 (틀림! 맵 기준으로는 0.03이어야 함) // → 원이 실제 위치보다 훨씬 오른쪽으로 표시됨

MAJOR 버그 2 — 흰 픽셀 노이즈: UI 텍스트·지명·도로도 검출

자기장 원 테두리(흰 링)를 찾기 위해 r>200, g>200, b>200 픽셀을 수집하는데,
PUBG 전체맵에는 흰 픽셀이 아주 많음.
// circle.service.ts:25 if (r > 200 && g > 200 && b > 200) { points.push([x, y]); } // 화면에 존재하는 흰 픽셀들: // - 지도 위 도시 이름 텍스트 (Pochinki, Rozhok, ...) // - 도로 라인 // - 그리드 라인 // - 미니맵 테두리 // - 탄약/아이템 UI 텍스트 // → 이 모든 점들이 원 피팅에 들어가서 엉뚱한 원이 생성됨

MINOR 버그 3 — Docker NEXT_PUBLIC 환경변수 빌드 타임 이슈

Next.js의 NEXT_PUBLIC_* 변수는 빌드 시점에 번들에 포함됨.
docker-compose.yml에서 environment로 전달해도, docker build 시점에는 해당 값이 없어서
프론트엔드가 fallback 값인 http://localhost:3001을 사용하게 됨.
// docker-compose.yml frontend: environment: NEXT_PUBLIC_CAPTURE_SERVICE_URL: http://127.0.0.1:3001 # ← 빌드 타임에 미적용! // useCaptureSocket.ts const CAPTURE_SERVICE_URL = process.env.NEXT_PUBLIC_CAPTURE_SERVICE_URL ?? 'http://localhost:3001'; // 위 환경변수가 빌드에 없으면 항상 localhost:3001 사용 (이 경우엔 우연히 맞을 수 있음)

버그 1 시각화 — 좌표 불일치

왼쪽: 실제 캡처된 화면 구조 / 오른쪽: CircleOverlay가 렌더링하는 좌표 공간

해결책 선택지

✅ 안 A — 청록색 경계로 맵 영역 자동 검출 (추천)

  • MapDetection에서 청록 픽셀의 bounding box를 반환
  • CircleService에서 해당 영역만 crop해서 원 검출
  • 정규화를 crop 영역 크기 기준으로 변경
  • 노이즈(UI 텍스트 등)도 자동으로 제외됨
장점: 해상도 무관, 맵 크기 자동 적응, 노이즈 격리
단점: MapDetection 반환값 타입 변경 필요

안 B — 해상도별 하드코딩 crop 좌표

  • 1920×1080, 2560×1440 등 해상도별로
  • 맵 영역의 left/top/width/height를 상수로 정의
  • 해당 영역만 crop해서 분석
장점: 구현 단순, 빠름
단점: 해상도 바뀌면 새로 측정해야 함, 유지보수 어려움

안 C — 흰색 링 픽셀 필터 강화

  • 흰 픽셀 중 주변에 파란색(자기장)이 있는 것만 선택
  • 엣지 감지 + 원형 구조 필터 적용
장점: 정밀도 높음
단점: 구현 복잡, 성능 저하 우려

안 D — 파란 위험 구역 직접 검출

  • 흰 링 대신 파란(r<80, b>150) 픽셀을 검출
  • 파란 영역의 내부 경계를 원으로 피팅
  • 전체맵에서 파란 색은 바다(청록)와 자기장(파란)이 다름
장점: 자기장 색이 뚜렷해서 검출 쉬움
단점: 바다 색과 구분 로직 추가 필요

추천 구현 순서

  1. 안 A 채택: MapDetection.isMapOpen() → MapDetection.detectMapArea() 반환값 변경 (boolean → MapArea | null)
  2. CircleService.extractCircle()가 MapArea를 받아 해당 영역만 crop
  3. 정규화: x = (cx - mapLeft) / mapWidth, y = (cy - mapTop) / mapHeight, r = r / mapWidth (정사각형 가정)
  4. 흰 픽셀 필터에 추가 조건: 인접 픽셀에 파란색이 있는 경우만 (옵션)
  5. Docker NEXT_PUBLIC 이슈: Dockerfile에 ARG로 빌드 타임 전달하도록 수정
