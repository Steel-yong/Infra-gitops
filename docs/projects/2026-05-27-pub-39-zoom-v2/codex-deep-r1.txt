**핵심 결론**

체인안은 “되면 정확하지만, 제품의 주 경로로 두면 안 되는 취약한 보조 경로”입니다. 이유는 단순합니다. 유저가 후반에 보는 실제 입력은 “확대한 맵 한 번, 한 원 일부, 아주 짧은 시간”인데, 체인안은 “이전 원과 현재 원이 동시에 보이는 좋은 프레임”을 요구합니다. 최우선 조건인 유저 편의성 변수 최소와 정면으로 충돌합니다.

가장 강한 방향은 단일 프레임에서 `줌 viewport의 절대 위치`를 먼저 복원하고, 그 위에 이미 아는 `페이즈 반경`과 검출된 자기장 픽셀을 얹는 것입니다. 수식상 페이즈 반경으로 scale은 고정됩니다. 남는 것은 translation 하나입니다. 즉, 단 한 개의 절대 앵커만 있으면 현재 원 중심은 바로 절대좌표가 됩니다.

**1. 체인안 가혹 비판**

체인안의 전제는 생각보다 많습니다.

- 이전 원의 절대좌표가 이미 정확해야 합니다.
- 현재 프레임에 이전 원과 현재 원이 둘 다 보여야 합니다.
- 두 원을 픽셀상에서 안정적으로 분리해야 합니다.
- 현재 페이즈 OCR이 맞아야 합니다.
- 이전 원이 화면 밖으로 나가거나 UI에 가려지면 안 됩니다.
- 사용자가 후반에 아주 짧게 본 프레임에서도 충분한 arc가 있어야 합니다.
- 이전 단계의 오차가 다음 단계로 전파되지 않아야 합니다.

깨지는 상황은 후반일수록 늘어납니다.

4·5페이즈에서 사용자가 맵을 잠깐만 열면 원 하나만 보일 가능성이 큽니다. 이전 원은 화면 밖이거나 거의 안 보입니다. 새 자기장이 작고, 흰 선 픽셀은 UI, 지형선, 텍스트와 섞입니다. RANSAC inlier 25~39%는 “검출이 가능하다”는 뜻이지 “동시 두 원 분해가 안정적이다”는 뜻이 아닙니다.

더 치명적인 건 체인 누적오차입니다. 1페이즈 앵커가 0.5% 틀리고, 2페이즈 원 fitting이 0.7% 틀리고, 3페이즈에서 이전 원이 일부만 보이면, 5페이즈에는 “그럴듯하지만 틀린 원”이 됩니다. 사용자는 그 오류를 교전 중에 검증할 방법이 없습니다. 틀린 자기장 안내는 없는 것보다 나쁩니다.

체인안의 진짜 가치는 fallback입니다. “이전 원과 현재 원이 둘 다 보이면 강한 제약으로 보정한다.” 정도가 맞습니다. 메인 로컬라이저로 두면 후반 짧은 glance 문제를 해결하지 못합니다.

**2. 단일 짧은 줌 glance 절대좌표 복원 방법들**

**A. 도시라벨·격자 OCR 앵커.**

원리. 확대 전체맵에서 도시명, 격자 문자, 격자선, 좌표 라벨을 OCR로 읽습니다. `School`, `Pochinki`, `Georgopol`, `I`, `J`, `7`, `8` 같은 텍스트는 게임 렌더와 기준맵 외형 차이에 덜 민감합니다. 페이즈 반경으로 scale을 고정하고, OCR로 읽은 라벨의 화면 위치와 기준맵 절대 위치를 앵커로 써서 viewport translation을 구합니다.

왜 무마찰인가. 사용자는 그냥 평소처럼 확대 맵을 봅니다. 추가 행동이 없습니다.

정확도. 라벨 하나가 정확히 잡히면 매우 높습니다. scale은 페이즈 반경이 주고, 라벨은 translation을 줍니다. 도시명 중심 위치 오차와 OCR 박스 중심 오차가 핵심입니다. 격자선까지 같이 쓰면 더 강합니다.

실패모드. 후반 원 주변이 야지거나 바다 쪽이면 라벨이 없을 수 있습니다. 확대 배율이 높으면 텍스트 일부만 보일 수 있습니다. 한글·영문 설정, 방송 UI, 색상 대비, 텍스트 가림에 취약합니다. 격자 문자는 `I`와 `1`, `O`와 `0` 혼동이 생깁니다.

난이도. 중상입니다. OCR 자체보다 “라벨 후보를 지리적으로 제약하고, 잘못 읽은 라벨을 기각하는 로직”이 중요합니다.

**B. 98영상 기반 줌 crop 절대위치 ML.**

원리. 확대 맵 crop을 입력하면 기준맵 위의 위치 heatmap과 zoom scale을 예측하는 모델을 학습합니다. 고전 SIFT가 게임렌더와 기준맵 외형 차이 때문에 깨졌다면, 고전 feature가 아니라 domain-invariant descriptor를 학습해야 합니다. DINOv2/CLIP류 feature, Siamese retrieval, dense correspondence, synthetic crop 생성, 방송 영상 weak label을 섞는 방식이 맞습니다.

왜 무마찰인가. 사용자는 아무것도 하지 않습니다. 맵 crop 한 장만 들어오면 됩니다.

정확도. 잘 만들면 가장 강력합니다. 특히 라벨이 없는 산악, 해안, 도로 교차, 강 모양, 건물 밀도 같은 약한 단서들을 결합할 수 있습니다. 단, 학습 데이터 라벨 품질이 낮으면 확신도만 높은 헛소리를 합니다.

실패모드. 기준맵과 실제 렌더 차이, 계절·맵 업데이트, 태이고·에란겔 스타일 차이, UI 가림, motion blur, 압축 artifacts, 매우 균질한 숲·논밭 지역에서 깨집니다. 98편은 많아 보이지만 “모든 줌 배율·모든 지역·모든 UI 상태”를 커버하기엔 부족할 수 있습니다.

난이도. 매우 높습니다. 단순 분류가 아니라 좌표 회귀와 불확실도 추정이 필요합니다. 하지만 시간과 노력이 무관하고 정확도·무마찰이 최우선이면 투자할 가치가 있습니다.

**C. 항상 켜진 미니맵 기반 플레이어 절대위치 앵커.**

원리. 미니맵은 항상 보입니다. 미니맵 중심이 거의 플레이어 위치라면, 미니맵 crop을 기준맵에 로컬라이즈해 플레이어 절대좌표를 얻습니다. 이후 확대 전체맵 glance에서 플레이어 아이콘이 보이거나, 화면 중심·사용자 관심 위치가 플레이어 주변이라는 약한 prior와 결합합니다. 미니맵에 자기장 경계가 보이면 현재 원의 국소 접선·곡률·상대거리도 얻습니다.

왜 무마찰인가. 사용자는 맵을 열지 않아도 미니맵은 계속 제공됩니다. 후반 짧은 glance 이전부터 tracker가 누적 상태를 가질 수 있습니다.

정확도. 플레이어 위치는 고정 앵커로 매우 가치가 큽니다. 전체맵에서 플레이어 아이콘까지 보이면 단일 앵커가 되어 현재 원 절대좌표가 바로 복원됩니다. 전체맵에 플레이어 아이콘이 안 보이면 단독으로는 약해지고, prior 역할이 됩니다.

실패모드. 미니맵 crop이 작고 회전 여부, 축척 변화, 차량 속도, 지형 반복성 때문에 로컬라이즈가 어렵습니다. 전투 중 연막·UI·관전 UI 차이가 있으면 더 어렵습니다. 미니맵 중심이 항상 플레이어인지 실제 확인이 필요합니다.

난이도. 중상입니다. 기존 PUB-40 방향과 맞고, 제품 가치도 큽니다. 다만 “미니맵만으로 전체맵 원 중심”까지 바로 가는 것은 과장입니다. 플레이어 위치 앵커와 자기장 국소 경계를 결합해야 합니다.

**D. 전체맵 내 플레이어 아이콘 앵커.**

원리. 사용자가 확대 전체맵을 열었을 때 본인 위치 아이콘이 보이면, 그 픽셀 위치와 미니맵 tracker의 절대 플레이어 좌표를 앵커로 씁니다. 페이즈 반경으로 scale은 이미 고정되므로, 플레이어 아이콘 하나만으로 viewport translation이 결정됩니다. 그 다음 검출된 자기장 원 중심을 절대좌표로 변환합니다.

왜 무마찰인가. 사용자가 자연스럽게 보는 확대 맵을 그대로 씁니다. 별도 행동이 없습니다.

정확도. 플레이어 아이콘이 보이는 프레임에서는 최상급입니다. 도시라벨보다 더 동적이고 현재성 있는 앵커입니다.

실패모드. 사용자가 원 중심이나 다음 이동지를 보기 위해 플레이어가 화면 밖인 확대 영역을 볼 수 있습니다. 아이콘이 자기장 선, 팀 마커, 핑과 겹칠 수 있습니다. 솔로·듀오·스쿼드 UI 차이가 있습니다.

난이도. 중간입니다. 아이콘 검출만 잘 되면 기하가 단순합니다.

**E. 격자선 기반 절대좌표 복원.**

원리. PUBG 전체맵의 격자선은 렌더 차이에 비교적 강합니다. 확대 화면에서 수직·수평 grid line 간격을 찾고, 격자 문자 OCR 또는 도시라벨로 grid index를 정합니다. 페이즈 반경 scale과 grid spacing scale을 교차검증합니다.

왜 무마찰인가. 자연 입력입니다.

정확도. grid index가 맞으면 높습니다. scale sanity check 용도로도 좋습니다.

실패모드. 확대 배율이 높으면 격자 문자 없이 격자선만 보여 index가 모호합니다. 격자선은 반복 패턴이라 단독으로 translation이 정해지지 않습니다. 라벨이나 ML prior가 필요합니다.

난이도. 중간입니다.

**F. 미니맵 자기장 경계의 국소 기하 활용.**

원리. 미니맵에는 플레이어 주변 자기장 경계가 보일 수 있습니다. 플레이어 절대좌표를 알고, 페이즈 반경도 알고, 미니맵에서 경계까지의 방향과 거리를 알면 원 중심 후보는 기하적으로 크게 줄어듭니다. 경계 점 `B`, 플레이어 `P`, 반경 `R`이 있으면 원 중심은 `B`에서 법선 방향으로 거리 `R`인 후보입니다. 여러 프레임을 누적하면 후보가 수렴합니다.

왜 무마찰인가. 항상 켜진 미니맵만 사용합니다.

정확도. 경계가 미니맵에 여러 번 보이면 강합니다. 후반일수록 원이 작고 경계가 자주 가까워져 가치가 커집니다.

실패모드. 경계가 미니맵에 안 보이면 정보가 없습니다. 미니맵 경계 픽셀과 실제 원 경계가 시각적으로 애매할 수 있습니다. 접선 방향 추정이 틀리면 중심 후보가 크게 흔들립니다.

난이도. 높음입니다. 하지만 후반 문제에 직접 맞습니다.

**G. Bayesian factor graph / particle filter 통합.**

원리. 단일 방법에 올인하지 않고, 모든 관측을 factor로 넣습니다. 관측은 OCR 라벨, grid, 플레이어 위치, 미니맵 경계, 현재 원 arc, 이전 원, ML heatmap입니다. 상태는 `viewport transform`, `current circle center`, `phase`, `player position`입니다. 각 factor는 확률 분포와 신뢰도를 가집니다. 가장 그럴듯한 절대좌표와 불확실도를 출력합니다.

왜 무마찰인가. 사용자는 아무것도 하지 않습니다. 시스템 내부에서 증거를 합칩니다.

정확도. 제품 수준에서는 이게 최종 형태여야 합니다. 한 관측이 틀려도 다른 관측이 잡아줍니다.

실패모드. 잘못된 confidence calibration이 가장 큰 위험입니다. 틀린 ML이 너무 높은 신뢰도를 내면 전체가 망가집니다. 디버깅이 어렵습니다.

난이도. 매우 높음입니다. 하지만 “정확도와 무마찰 최우선” 조건에서는 정답에 가깝습니다.

**H. 1페이즈 unzoom 앵커를 지도로 저장하는 초기 보정.**

원리. 시작 때 잠깐 나오는 unzoom 전체맵에서 기준맵과 정렬해 전역 보정값을 얻습니다. 이후 확대 맵은 이 보정값과 페이즈 반경, 라벨·플레이어·ML 관측으로 해결합니다.

왜 무마찰인가. 유저가 의식적으로 하는 행동은 없습니다. 자연스럽게 나오는 프레임을 잡습니다.

정확도. 초반에는 좋습니다. 그러나 후반 단일 glance 문제를 혼자 해결하지 못합니다.

실패모드. 1페이즈 프레임 캡처 실패, 맵 선택 오류, 화면공유 시작 타이밍 늦음, 게임 재시작, 관전 UI 차이입니다.

난이도. 중간입니다.

**4. 정확도와 무마찰 기준 Top 3**

1. Factor graph 통합형 로컬라이저.

이게 최종 제품 아키텍처로 가장 맞습니다. 단일 기술을 믿으면 반드시 깨집니다. 후반 짧은 glance에서는 OCR이 없을 수 있고, 플레이어 아이콘이 안 보일 수 있고, ML이 애매할 수 있고, 체인은 끊길 수 있습니다. 하지만 이 관측들을 확률적으로 합치면 “이번 프레임에서 가능한 것만” 쓸 수 있습니다. 유저 편의성 변수는 0입니다.

핵심은 `정답 하나`가 아니라 `좌표 + 신뢰도 + 대체 후보`를 내는 것입니다. 신뢰도 낮으면 UI에 확정 원을 그리지 말고 “추정 약함” 상태로 처리해야 합니다. 틀린 확정 표시가 최악입니다.

2. 98영상 기반 ML 로컬라이저 + OCR/grid 보정.

단 한 번의 확대 crop만으로 절대 viewport를 찾는 가장 무마찰적인 메인 엔진입니다. 고전 feature matching이 실패한 이유가 “특징점이 없다”가 아니라 “도메인 차이를 견디는 feature가 아니다”라면, 학습형 descriptor가 정공법입니다. 라벨과 격자는 ML의 hallucination을 기각하는 안전장치로 붙여야 합니다.

단, 단순 좌표 regression은 위험합니다. reference map 위 heatmap retrieval로 만들어야 합니다. 후보 Top-K를 내고, 페이즈 반경으로 얻은 scale, OCR 라벨, grid spacing, 원 arc, 미니맵 플레이어 prior로 rerank 해야 합니다.

3. 미니맵 기반 플레이어·자기장 경계 tracker.

후반 문제에 가장 잘 맞습니다. 전체맵 glance가 짧을수록, “glance 이전부터 계속 쌓이는 정보”가 중요합니다. 미니맵은 항상 켜져 있고, 플레이어 위치와 주변 자기장 경계는 후반일수록 의미가 커집니다. 전체맵에서 원 하나만 보여도, 미니맵 tracker가 viewport 앵커나 원 중심 후보를 제공하면 끊김이 줄어듭니다.

단, 미니맵만으로 모든 걸 해결한다고 보면 안 됩니다. 미니맵은 국소 관측입니다. 전역 위치가 틀리면 전체가 틀립니다. 따라서 ML/OCR/grid와 결합해야 합니다.

**추천 설계**

메인 경로는 이렇게 잡는 게 맞습니다.

1. 항상 미니맵 tracker를 돌려 플레이어 절대좌표와 주변 자기장 경계 후보를 누적합니다.
2. 확대 전체맵 glance가 들어오면 자기장 픽셀 원을 검출하고, OCR 페이즈 반경으로 scale을 고정합니다.
3. 같은 프레임에서 가능한 앵커를 모두 뽑습니다. 도시라벨, grid 문자, grid line, 플레이어 아이콘, ML viewport 후보, 이전 원 체인 후보입니다.
4. Factor graph로 viewport translation과 현재 원 중심을 jointly solve 합니다.
5. 신뢰도 높은 경우만 확정 원으로 표시합니다. 낮으면 후보 원 또는 보류로 처리합니다.

체인안은 6번째 보조 factor로 내려야 합니다. 지금 안의 약점은 구현 난이도가 아니라 제품 가정입니다. “후반에 사용자가 짧게 한 번 확대해서 본다”가 진짜 제약이면, 동시 두 원 체인은 중심 설계가 될 수 없습니다.
