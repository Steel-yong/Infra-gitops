# 자기장 페이즈 1 검출 — 결정 사항 기록

## 사용자가 명시한 핵심 제약

1. **페이즈 1만 먼저 완성.** 페이즈 1이 안 되면 다른 페이즈도 무의미.
2. **자기장이 줄어드는 시점 ≠ 검출 시점.** 대기 시간(흰 원만, 외부 파란 없음)에 검출하는 게 진짜 가치.
3. **페이즈 1 줄어드는 중도 초반엔 외부 파란 안 보임** (자기장이 맵 끝에서 시작해서 파란 영역이 화면 밖). 페이즈 2~8은 줄어드는 중 외부 파란 정상.
4. **흰 원이 두 상태(대기·줄어듦) 모두에서 공통 단서.** 색 기반 검출 불가.
5. **이번 세션 자율 반복 허용.** 사용자 질문 안 함. 성공하면 종료.

## 이번 세션에서 내린 결정

### 결정 1 — 검출 알고리즘 본질 교체

이전 알고리즘: "비-파란 픽셀의 평균 좌표 + 거리 분포 90 percentile"
- 문제: 자기장 외부가 일반 맵일 때(대기 중) 동작 불가
- 문제: 노이즈에 평균이 끌림
- 결정: **흰 원 자체 검출 (Hough Circle 계열)** 로 전면 교체

### 결정 2 — OpenCV.js 의존 추가 안 함 (우선)

- 이유: WASM 초기화·Node 환경 호환성 리스크
- 대안: TypeScript로 RANSAC 또는 직접 Hough 구현
- 만약 직접 구현 다 실패하면 → OpenCV.js 시도

### 결정 3 — 분모 8160m 유지

출처: `documentation.pubg.com/en/telemetry-objects.html` (PUBG 공식 telemetry).
플레이어블 영역 816,000cm × 816,000cm.
이전 8000m → 8160m 보정 완료 후 재정정 (사용자 표 적용).

### 결정 4 — 동적 OCR 보정 측정 구간 확대

- `useOcrTimer.ts` lag 측정을 OCR 호출 → tick 시작으로 확대
- setInterval 큐잉 + 전처리 + OCR 처리 다 잡힘
- 이전 약 0.5s 측정 → 약 1.0~1.5s 실측

### 결정 5 — `useAlertTimer` 무한 루프 픽스

- 원인: page.tsx onAlert 매 렌더마다 새 함수 → useCallback dep 변동 → setState 무한
- 픽스: `useAlertTimer.ts` setDisplayState를 함수형 + 같은 값이면 prev 반환
- 외과적, 사용자 코드(page.tsx) 수정 없음

### 결정 6 — `CircleData`에 `phase?: number` 추가

- 백엔드에서 검출한 페이즈를 프론트로 전달
- TimerPanel에 "현재 페이즈: N페이즈 (검출 반경 추정값)" 표시
- 디버깅용. 진짜 페이즈는 OCR 직접 추출이 추후 작업

### 결정 7 — 검증 자동화

사진 2장(1페이즈.png, 배그 맵화면.png)을 ground truth로:
- `extractCircle(base64)` 호출 → 반경·중심 추출
- 반경: 0.24474 ±10% 안
- 중심: 사진 시각 중심과 ±5% 안
- 둘 다 통과 → PASS, 알고리즘 채택

PASS 못 하면 다른 가설로.

## 가설 우선순위

1. **A — 흰 픽셀 RANSAC** (가장 직관적, 라이브러리 0)
2. **C — 노란 점 검출** (가장 단순, 백업)
3. **B — Hough Circle 직접 구현** (정통)
4. **D — 색 전환 엣지 + RANSAC**
5. **E — Canny edge + 페이즈 한정 Hough**

## 도메인 지식 — PUBG 자기장 시각 특성

- 흰 원 둘레가 자기장 경계 (선명, 굵음, 거의 완벽한 원)
- 자기장 중심에 노란 점(다음 자기장 마커) 표시됨 — 검증용 보조
- 자기장 안에 빨간 채움 = 다음 페이즈가 작아질 예고 영역 (대기 시간에 표시)
- 격자선 매우 흐림 (확대 케이스 단서로는 약함)
- 도시명 텍스트 보임 (Map Registration 단서 가능)

## 좌표계

- `CircleData.x, y, r` = 0~1 정규화
- y는 이미지 좌표계 (위 0 → 아래 1)
- Leaflet `CRS.Simple` 변환: `[1 - y, x]` (CLAUDE.md 5부 명시)
- 정규화 분모: 맵 영역 한 변 (화면 중앙 정사각형, 1080×1080)
- 이전 코드는 화면 전체 너비/높이로 정규화 → 맵 영역 crop 후 정규화로 정정

## 결정 9 — 두 모드 분기 (사용자 도메인 룰 반영, 2026-05-15 추가)

사용자 추가 통찰:
- **페이즈 1만 예외**: 자기장이 처음 생기는 단계 → 외부 파란 없음.
- **페이즈 2~8 모두**: 이전 자기장이 줄어들어 새 자기장이 안에 그려짐 → **외부 항상 파란**.

이걸 그대로 알고리즘에 박음.

### 모드 분기

```
파란 비율 측정
  < 5%  → 페이즈 1 모드 (흰 픽셀 RANSAC, 페이즈 1 반경만)
  ≥ 5%  → 페이즈 2~8 모드 (파란 경계 RANSAC, 페이즈 1~8 모두 후보)
           → 실패 시 페이즈 1 흰 픽셀 RANSAC fallback (페이즈 1 줄어드는 중 케이스)
```

### 파란 경계 RANSAC — 페이즈 후반 핵심

```
1. 파란 픽셀 중 인접 4픽셀에 비파란이 있는 픽셀 추출 = 자기장 둘레
2. 그 점들로 RANSAC (페이즈 1~8 후보 반경 ±20%)
3. 점수 = 둘레 ±2px 위 같은 단서의 픽셀 수
```

이 단서가 강한 이유:
- 흰 색 의존 없음 — 색 전환(파란/비파란) 자체로 판정
- 페이즈 8(반경 2.7px)까지도 둘레 전환 픽셀 수 명확
- 자기장 외부 파란이 있는 한 (페이즈 2~8 모든 단계) 작동

### 한계 보존

- 페이즈 7~8 점수 임계 floor 12점은 그대로 — false positive 위험 있음
- 패닝 미지원 — 진짜 풀이는 도시명 OCR 또는 ORB

## 결정 8 — 페이즈 1~8 통합 RANSAC + 격자선 확대 비율 (2026-05-15 추가)

사용자 게임 검증 결과:
- 페이즈 1 검출 잘 동작 ✓
- 자기장 미표시 상태에서 false positive 없음 ✓ (흰 원 점수 < 200 → null)
- 페이즈 2~9 + 확대 대응 요청

### 통합 RANSAC

stateless 설계 유지. 페이즈 1~8 각각의 반경 후보 위에서 통합 검색:

1. 무작위 3점으로 원 결정 → 반경 r 측정
2. r이 페이즈 N의 (반경 × 스케일 ± 20%) 범위에 속하면 페이즈 N 후보로 분류
3. 첫 매칭 페이즈 채택 (페이즈 1부터 8 순)
4. 점수 = 둘레 ±2px 위 흰 픽셀 수
5. 페이즈별 점수 임계 (반경 비례, 최소 12점 floor)

페이즈별 최소 점수:
- phase 1: 200
- phase 2: 110
- phase 3: 60
- phase 4: 33
- phase 5: 17
- phase 6: 12 (floor)
- phase 7: 12 (floor)
- phase 8: 12 (floor)

페이즈 후반(7, 8)은 반경이 너무 작아 점수만으로 신뢰 어려움 → false positive 위험 → 추후 노란 점 마커 검증 강화 또는 tracking(이전 페이즈 +1) 도입 필요.

### 격자선 확대 비율 (Stage 0)

PUBG 1km 격자(맵 8칸) 간격을 측정해서 확대 비율 추정:

1. 행마다 회색~흰색 픽셀(R≈G≈B, 130~220) 개수 카운트
2. 평균 + 1.5σ 이상 행 = 격자선 후보
3. 인접 격자선 간격 측정 (5% 이상 떨어진 라인끼리만)
4. 간격 중앙값 = 격자 한 칸 픽셀 너비
5. (size / 8) / 격자 칸 너비 = 스케일
6. 스케일 0.7 ~ 3.0 사이면 채택, 아니면 null (1.0 fallback)

한계:
- 격자선이 흐릿하거나 자기장에 묻히면 검출 실패 (fallback 1.0)
- 패닝(화면 중심 ≠ 맵 중심) 처리 안 함 — 격자선만으로는 평행이동 모름
- 진짜 패닝까지 다루려면 도시명 OCR 또는 ORB 특징점 매칭 필요 (별도 작업)

### 한계 명시

- 확대 케이스의 패닝(화면이 맵 일부분만 보임)은 이번 안으로 부분 해결. 자기장 중심이 화면 안에 있다면 픽셀 좌표 그대로 정규화하지만, 화면 일부분만 보이면 그 좌표는 맵 전체 좌표가 아니라 화면 일부분 기준이라 우리 지도와 어긋날 수 있음.
- 진짜 패닝 + 확대를 다 풀려면 도시명 OCR 또는 맵 이미지 ORB 정합이 필수.
- 페이즈 7~8 false positive 위험 → 사용자 게임 검증 시 false positive 빈도 보고 임계값 또는 tracking 도입 결정.
