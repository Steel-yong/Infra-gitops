## 1. 단일 라인 수정 — `g < r + 25` → `g < r + 40`

### 결정

`apps/services/capture/src/capture/circle.service.ts:180` (`isBluePixel` 함수):

```ts
// 변경 전
g < r + 25 // 바다 제외 (바다는 G >> R)

// 변경 후
g < r + 40 // 바다와 위험 구역이 거의 동일 톤이라 임계값 완화 (측정 근거 §3)
```

### 이유

원래 가정 — "PUBG 위험 구역 파란 = R 강세, 바다 = G 강세" — 가 **틀림**. 실측 결과 둘 다 G가 R보다 평균 +25 더 큼. 현재 `g < r + 25` 조건이 진짜 위험 구역 픽셀의 45%만 통과시키고 55%를 "바다"로 오분류해 잘라냄.

### 적용

`circle.service.ts:180` 한 줄 수정. 다른 변경 없음.

## 2. 처음의 잘못된 분석 (기록용)

작업 초반에 두 가지 추측 기반 분석을 했고 둘 다 측정으로 반증됨. 다음 세션이 같은 함정에 안 빠지게 기록:

### 틀린 분석 1: "테이고는 바다라 외부 파란이 적다"

- 가정: 테이고는 작은 섬 맵이라 자기장 외부 위험 구역 영역 자체가 적어서 `blueRatio` 5% 못 넘김.
- 반증: 사용자 캡처(태2페/태3페/태4페) 측정 시 외부 파란 영역이 화면 70%+. 가정과 정반대.

### 틀린 분석 2: "에란겔/테이고 알고리즘 분리 필요"

- 가정: 두 맵 환경이 달라서 알고리즘 분리해야 함.
- 반증: 측정 결과 위험 구역과 바다 RGB 분포가 거의 동일 → 색만으로 둘을 구분 불가 → 분리해도 문제 해결 안 됨. 진짜 문제는 `g < r + 25` 임계값 자체.

### 교훈

추측 전에 raw 데이터 측정. PUB-30 페이즈 OCR ROI 사례 반복.

## 3. 측정 데이터 (PUBG 위험 구역 파란 RGB)

태이고 페이즈 2/3/4 raw 캡처 → 화면 중앙 정사각형 crop → 파란계 픽셀(b 우세) RGB 분포:

| | 페이즈 1 wait | 페이즈 2 | 페이즈 3 | 페이즈 4 |
|---|---|---|---|---|
| 파란계 픽셀 수 | 33 (~0%) | 55,118 | 62,641 | 65,413 |
| R 평균 | 49 | 48 | 48 | 48 |
| G 평균 | 61 | 73 | 73 | 73 |
| B 평균 | 115 | 145 | 144 | 144 |
| **G-R 평균** | **+12** | **+25** | **+25** | **+25** |
| 현재 `g<r+25` 통과 | 0.04% | 45.7% | 44.1% | 44.3% |
| 제안 `g<r+40` 통과 | **0.04%** | **99.6%** | **99.6%** | **99.6%** |
| 현재 `isBluePixel` 비율 | 0.04% | 34% | 38% | 39% |
| `g<r+25` 제거 시 | 0.04% | 75% | 86% | 89% |

### 핵심 관찰

1. **위험 구역 파란 G-R = +25** (페이즈 2/3/4 일관). 매우 안정.
2. **바다 G-R = +27** (태1 줄.png 외곽 측정). 위험 구역과 거의 동일.
3. **두 영역 RGB 거의 같음** — 색만으로 구분 물리적 불가. PUBG가 해양 맵에서 일관된 톤으로 렌더링한 듯.
4. **페이즈 1 wait는 외부 파란 0%** — 알고리즘 완화해도 false positive 위험 0.

### 임계값 선택 근거

- `g < r + 40` 페이즈 2/3/4 모두 99.6% 통과 → 위험 구역 픽셀 거의 모두 포함.
- `g < r + 50`도 100% 통과지만, 더 완화하면 다른 파란계 잡음까지 들어올 위험.
- `g < r + 40`이 가장 보수적이면서 충분한 임계값.

## 4. 에란겔 측정 안 함 (회귀 위험 평가)

### 결정

에란겔 raw 캡처 측정은 생략. 사용자가 "에란겔은 이미 잘 동작하고 회귀만 조심하면 된다" 판단.

### 이유

이론적 회귀 분석:
- 에란겔 위험 구역 파란이 진짜 R 강세(예: G-R = +5)였다면 → 현재 알고리즘으로도 잘 통과. 완화해도 더 통과만 함, 줄어들지 않음.
- 에란겔도 테이고처럼 G-R = +25였다면 → 사용자가 에란겔 잘 됐다고 했으니 절반 잘리고도 RANSAC 가능한 환경 (외부 영역 절대 크기 큼). 완화해도 더 잘됨.
- 어느 쪽이든 회귀 위험 없음.

### 잔여 위험

- 매우 작은 가능성: 에란겔 위험 구역에 false positive 만들 픽셀 패턴이 있을 수도. 사용자 시각 검증으로 확인.

## 5. 운영 로그 `파란 0~3.7%`의 진짜 원인 (별도 디버깅)

### 충돌

- 사용자 캡처 측정: 페이즈 2/3/4 `blueRatio` 34~39%
- 운영 로그: `파란 비율 0.0~3.7%`

10배 차이. 원인 불명. 가능성:

1. **OCR 페이즈 오인식** — hintPhase가 잘못 잡혀서 페이즈 3(작은 원) 기대 반경으로 페이즈 1(큰 원) 찾음. RANSAC 매칭 실패. 단 이건 blueRatio 측정값 영향 안 줌. 별 가능성.
2. **캡처 영역 차이** — frontend 화면공유 시 사용자가 "모니터 전체" 선택했다면 PUBG 게임 외 영역(검은 데스크탑)이 캡처에 포함. 중앙 정사각형 crop 시 게임 화면이 아닌 영역 분석됨 → `blueRatio` 매우 낮게 측정.
3. **JPEG 0.7 압축으로 색 shift** — `useScreenCapture`가 frame을 `toDataURL('image/jpeg', 0.7)`로 인코딩. 압축 시 청파랑 → 청록으로 색 변화 가능 → 더 많이 잘림.

### 검증 방법 (별도 작업)

- capture-service에 일회용 raw frame 저장 옵션 추가 → 운영 frame 직접 측정해서 차이 원인 짚기.
- PUB-32 마무리 후 추가 디버깅.

### 본 PR 적용

이 충돌은 알고리즘 완화 효과 자체와 무관. `g < r + 40`이면 운영 환경이 어떻든 더 잘 통과하므로 PUB-32 변경은 가치 있음. 운영 검증으로 충분성 판단.
